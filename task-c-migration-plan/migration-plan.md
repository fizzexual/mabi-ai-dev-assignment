## 1. Целева инфраструктура — препоръки по сървъри

### Сървър 1: WordPress сайт (tonkin.bg)

**Текущо състояние:** cPanel на Superhosting, управляван хостинг, без root достъп, MySQL ~15GB данни.

**Препоръка: Hetzner Cloud CPX21 + Hetzner Managed MySQL**

| Параметър | Детайли |
|-----------|---------|
| Сървър | Hetzner Cloud CPX21 — 3 vCPU (AMD), 4GB RAM, 80GB NVMe SSD |
| Цена | ~€7.49/месец за сървъра |
| База данни | Hetzner Managed Database (MySQL) — от €9.90/месец за DB-3 план |
| Дата център | Falkenstein или Nuremberg (Германия) — ниска латентност за България |
| Контролен панел | CloudPanel (безплатен) или RunCloud (~$8/месец) |

**Защо Hetzner:**
- Отлично съотношение цена/производителност — значително по-евтино от Superhosting за по-добри ресурси
- Дата центрове в Германия — ниска латентност (~15-20ms) от България
- Managed MySQL елиминира нуждата от ръчно управление на базата данни, автоматични бекъпи
- Пълен root достъп — гъвкавост за конфигурация, за разлика от cPanel
- Вградени snapshots и бекъпи (€1.20/месец за 20% от цената на сървъра)

**Алтернативи разгледани и отхвърлени:**
- **DigitalOcean:** По-скъп за еквивалентни ресурси (~$24/месец за 4GB RAM). Managed MySQL от $15/месец.
- **Cloudways:** Managed WordPress хостинг от ~$14/месец. Удобен, но по-малко контрол и по-скъп.
- **SiteGround (Bulgaria-based):** Добър за управляван WordPress, но ограничен при 15GB MySQL база данни — тарифните планове имат лимити.

### Сървър 2: Next.js приложение (my.tonkin.bg)

**Текущо състояние:** Contabo VPS, Node.js, env файлове с API ключове, ~2GB.

**Препоръка: Vercel (Pro план)**

| Параметър | Детайли |
|-----------|---------|
| Платформа | Vercel Pro |
| Цена | $20/месец на член от екипа |
| Edge мрежа | Глобален CDN с автоматично кеширане |
| CI/CD | Автоматичен деплой при push в Git |
| Env управление | Вграден мениджмънт на environment variables |

**Защо Vercel:**
- Next.js е създаден от Vercel — най-добрата възможна оптимизация и поддръжка
- Автоматичен CI/CD — push в Git = деплой. Без ръчна конфигурация
- Вградено управление на environment variables с разделение по среди (production, preview, development)
- Edge Functions и ISR (Incremental Static Regeneration) — по-бърз сайт за крайните потребители
- Автоматично скалиране — при пикове (напр. уебинар ден) платформата се адаптира
- Preview deployments — всеки PR получава собствен URL за тестване
- Нулево управление на сървъра — няма нужда от SSH, обновяване на пакети, мониторинг на uptime

**Алтернативи разгледани:**
- **Cloudflare Pages:** Безплатен/евтин, но има ограничения с Node.js runtime (Workers е различен от Node.js). Не всички Next.js функции се поддържат напълно.
- **Hetzner VPS + PM2:** По-евтино (~€4/месец), но изисква ръчно управление — деплой, SSL, мониторинг, обновявания. Не е оправдано за малък екип без DevOps.
- **Railway.app:** Добра алтернатива ($5/месец + usage), но по-малко зряла платформа от Vercel за Next.js.

### Сървър 3: Видео стриймър (incoming.tonkin.bg)

**Текущо състояние:** Contabo VPS, 100GB+ видео файлове (HLS), PHP скриптове, ffmpeg, cron задачи, Zoom webhook.

**Препоръка: Hetzner Dedicated Server AX42 + Hetzner Storage Box**

| Параметър | Детайли |
|-----------|---------|
| Сървър | Hetzner AX42 — AMD Ryzen 5 3600, 64GB RAM, 2x 512GB NVMe SSD |
| Цена | ~€44/месец |
| Съхранение | Hetzner Storage Box BX21 — 1TB, от €3.81/месец |
| Bandwidth | 20TB включен трафик |
| Допълнително | Cloudflare (безплатен план) пред сървъра за CDN и DDoS защита |

**Защо Hetzner Dedicated (а не cloud VPS):**
- **ffmpeg транскодиране** изисква реална CPU мощ — dedicated сървър дава предвидима производителност без "noisy neighbor" ефект
- **100GB+ видео файлове** — NVMe SSD дискове с бърз I/O за HLS streaming
- **20TB трафик/месец** — повече от достатъчно за 350 члена, които гледат видео
- **Storage Box** като допълнително хранилище/бекъп за видео архива — достъпен по SFTP, rsync, SMB
- Значително по-евтино от Contabo при по-добро хардуерно качество и поддръжка

**Алтернативи разгледани:**
- **AWS S3 + CloudFront:** Отлична скалируемост, но **скъпо** за 100GB+ видео с активно стрийминг — трафикът на CloudFront е $0.085/GB. При 1TB/месец трафик = ~$85 само за CDN.
- **Bunny CDN + Bunny Storage:** Евтин CDN ($0.01/GB EU), добър за доставка, но все пак е нужен сървър за ffmpeg и webhook обработка. Може да се ползва **в комбинация** с Hetzner — видео файловете се пушват към Bunny CDN за доставка.
- **Cloudflare R2 + Stream:** R2 е без egress такси, но Cloudflare Stream е $1/1000 минути + $5/1000 минути съхранение — при голям обем видео може да стане скъпо.

**Оптимална комбинация:**
- Hetzner Dedicated за обработка (ffmpeg, webhook, cron)
- Cloudflare (безплатен план) пред сървъра за кеширане и DDoS защита
- Опционално: Bunny CDN за видео доставка ако трафикът нарасне значително

## 2. Ред на миграция

### Препоръчителна последователност: Next.js → WordPress → Видео сървър

| Приоритет | Сървър | Обосновка |
|-----------|--------|-----------|
| **1-ви** | Next.js (my.tonkin.bg) | **Най-безопасен за първа миграция.** Малък обем (~2GB), без бази данни за синхронизиране, stateless приложение. Vercel деплой е обратим — ако нещо се обърка, Contabo VPS все още работи. Preview deployment позволява пълно тестване преди DNS промяна. |
| **2-ри** | WordPress (tonkin.bg) | **Среден риск.** 15GB MySQL база изисква внимателна миграция, но WordPress миграцията е добре документиран процес. Има инструменти (WP-CLI, mysqldump, All-in-One WP Migration). Може да се тества на staging преди DNS промяна. |
| **3-ти** | Видео стриймър | **Най-сложен и рисков.** 100GB+ файлове изискват дни за трансфер. Активни cron задачи, Zoom webhook, ffmpeg обработка — много движещи се части. Мигрира се последен, за да има максимално време за подготовка и тестване. |

**Логика на подредбата:**

1. Започваме с най-малкия и най-обратимия компонент (Next.js), за да спечелим увереност и да изгладим процеса.
2. WordPress е вторият, защото е критичен (публичният сайт), но миграцията е стандартна процедура.
3. Видео сървърът е последен, защото трансферът на 100GB+ отнема реално време и изисква паралелна работа на двата сървъра.

## 3. Миграция на WordPress (tonkin.bg) — без прекъсване

### Стъпка по стъпка

#### Фаза 1: Подготовка (3-4 дни)

1. **Провизиране на нов Hetzner сървър**
   ```
   - Създаване на Hetzner Cloud CPX21 инстанция
   - Инсталиране на Ubuntu 22.04 LTS
   - Инсталиране на CloudPanel (или RunCloud) за управление
   - Конфигуриране на Nginx, PHP 8.2+, MySQL 8.0
   - Настройка на Let's Encrypt SSL сертификат (временно с Hetzner IP)
   ```

2. **Провизиране на Hetzner Managed MySQL**
   ```
   - Създаване на DB-3 инстанция
   - Whitelist на IP адреса на новия сървър
   - Създаване на база данни и потребител за WordPress
   ```

3. **Намаляване на DNS TTL**
   ```
   - 7 дни преди миграцията: намаляване на TTL от стандартен (3600s или повече) до 300s (5 минути)
   - Това гарантира, че при DNS промяна старите записи ще изтекат бързо
   - Проверка с: dig tonkin.bg +short и dig tonkin.bg SOA
   ```

#### Фаза 2: Копиране на сайта (1-2 дни)

4. **Експорт на базата данни от Superhosting**
   
   **Вариант А — чрез phpMyAdmin (ако mysqldump не е достъпен):**
   ```
   - Вход в cPanel → phpMyAdmin
   - Избиране на базата → Export → Custom → SQL формат
   - Отметка на "Add DROP TABLE" и "CREATE TABLE"
   - При 15GB база: ползване на Compress (gzip) за по-малък файл
   ```
   
   **Вариант Б — чрез SSH/WP-CLI (ако има SSH достъп):**
   ```bash
   # На стария сървър
   wp db export tonkin_backup_$(date +%Y%m%d).sql --add-drop-table
   gzip tonkin_backup_*.sql
   ```
   
   **Вариант В — чрез плъгин All-in-One WP Migration:**
   ```
   - Инсталиране на плъгина в WordPress
   - Export → File (може да има лимит 512MB в безплатната версия)
   - За 15GB база: ползване на "Unlimited Extension" (~$69) 
     ИЛИ ръчен подход с mysqldump + файлова система
   ```
   
   **Препоръка за 15GB база:** Ръчен подход с mysqldump + rsync е най-надеждният.

5. **Копиране на файловете**
   ```bash
   # На стария сървър (или чрез cPanel File Manager → Compress → Download)
   cd /home/username/public_html
   tar czf wordpress_files.tar.gz .
   
   # Трансфер към новия сървър
   scp wordpress_files.tar.gz root@NEW_SERVER_IP:/var/www/tonkin.bg/
   
   # На новия сървър
   cd /var/www/tonkin.bg
   tar xzf wordpress_files.tar.gz
   chown -R www-data:www-data .
   ```

6. **Импортиране на базата данни в Hetzner Managed MySQL**
   ```bash
   # На новия сървър
   mysql -h MANAGED_DB_HOST -u wordpress_user -p wordpress_db < tonkin_backup.sql
   ```

7. **Обновяване на wp-config.php**
   ```php
   define('DB_HOST', 'MANAGED_DB_HOST:PORT');
   define('DB_NAME', 'wordpress_db');
   define('DB_USER', 'wordpress_user');
   define('DB_PASSWORD', 'SECURE_PASSWORD');
   ```

#### Фаза 3: Тестване преди DNS промяна

8. **Тестване чрез hosts файл (най-важната стъпка!)**
   ```
   # На локалния компютър: редактиране на /etc/hosts (Linux/Mac) 
   # или C:\Windows\System32\drivers\etc\hosts (Windows)
   
   NEW_SERVER_IP    tonkin.bg
   NEW_SERVER_IP    www.tonkin.bg
   ```
   Това пренасочва само вашия компютър към новия сървър — останалите потребители продължават да ползват стария.

9. **Проверки за тестване:**
   - [ ] Главната страница зарежда ли се правилно?
   - [ ] Административният панел (/wp-admin) работи ли?
   - [ ] Изображения и медии зареждат ли се?
   - [ ] Контактни форми работят ли?
   - [ ] WooCommerce/плащания (ако има) функционират ли?
   - [ ] SSL сертификатът е ли валиден?
   - [ ] Permalink структурата работи ли? (Nginx rewrite rules)
   - [ ] Производителност — страниците зареждат ли се бързо?
   - [ ] Проверка на PHP error logs за грешки

10. **Алтернативен метод за тестване — временен домейн:**
    ```
    - Конфигуриране на staging.tonkin.bg → NEW_SERVER_IP
    - Инсталиране на WP-CLI на новия сървър
    - wp search-replace 'tonkin.bg' 'staging.tonkin.bg' --dry-run
    - wp search-replace 'tonkin.bg' 'staging.tonkin.bg'
    - Тестване на staging.tonkin.bg
    - След успешен тест: wp search-replace 'staging.tonkin.bg' 'tonkin.bg'
    ```

#### Фаза 4: DNS промяна (zero-downtime)

11. **Финална синхронизация преди DNS промяна**
    ```bash
    # Повторен експорт на базата данни (за да хванем промените от последните дни)
    # На стария сървър:
    wp db export final_sync.sql
    
    # Импорт на новия:
    mysql -h MANAGED_DB_HOST -u user -p db < final_sync.sql
    
    # Синхронизиране на нови медия файлове:
    rsync -avz --progress user@OLD_SERVER:/public_html/wp-content/uploads/ /var/www/tonkin.bg/wp-content/uploads/
    ```

12. **Промяна на DNS записите**
    ```
    - В DNS мениджъра (Cloudflare препоръчително):
      A запис: tonkin.bg → NEW_SERVER_IP
      A запис: www.tonkin.bg → NEW_SERVER_IP
    - TTL вече е 300s, така че промяната ще се разпространи за 5-10 минути
    ```

13. **Временен "read-only" режим на стария сървър**
    ```
    - Опционално: включване на maintenance mode на стария WordPress
      wp maintenance-mode activate
    - Или: блокиране на wp-admin с .htaccess за предотвратяване на промени
    - Това предотвратява ситуация, в която потребител пише в старата база данни,
      докато DNS-ът се разпространява
    ```

14. **Мониторинг след DNS промяна**
    ```bash
    # Проверка на DNS разпространение
    dig tonkin.bg +short  # трябва да показва новия IP
    
    # Проверка от различни локации
    # https://www.whatsmydns.net/#A/tonkin.bg
    
    # Мониторинг на error logs на новия сървър
    tail -f /var/log/nginx/tonkin.bg-error.log
    ```

15. **Връщане на TTL на нормални стойности**
    ```
    - След 48 часа стабилна работа: TTL обратно на 3600s
    - Изключване на стария Superhosting акаунт след 7 дни (оставяме го като бекъп)
    ```

## 4. Миграция на Next.js приложението (my.tonkin.bg)

### Стъпка по стъпка

#### Фаза 1: Подготовка на Vercel

1. **Създаване на Vercel акаунт и проект**
   ```
   - Регистрация на vercel.com с GitHub/GitLab акаунт
   - Импортиране на Git хранилището с Next.js кода
   - Vercel автоматично разпознава Next.js и конфигурира build процеса
   ```

2. **Управление на Environment Variables (критично!)**
   
   **Стъпки за сигурно управление на API ключове:**
   
   а) **Инвентаризация на env файловете:**
   ```bash
   # На Contabo VPS — списък на всички env променливи
   cat /path/to/app/.env.production
   # Документиране на всяка променлива: какво прави, откъде идва, трябва ли да се ротира
   ```
   
   б) **Добавяне във Vercel Environment Variables:**
   ```
   - Vercel Dashboard → Project → Settings → Environment Variables
   - За всяка променлива:
     - Име: DATABASE_URL, API_KEY, и т.н.
     - Стойност: съответната стойност
     - Среди: Production, Preview, Development (по избор)
   - Чувствителните стойности се криптират и не се показват в логове
   ```
   
   в) **Vercel CLI за bulk добавяне:**
   ```bash
   # Инсталиране на Vercel CLI
   npm i -g vercel
   
   # Добавяне на env променливи от файл
   vercel env add VARIABLE_NAME production
   # или чрез .env файл
   vercel env pull .env.local  # за сваляне
   ```
   
   г) **Допълнителна сигурност — dotenv-vault (опционално):**
   ```bash
   # dotenv-vault позволява версиониране и криптиране на .env файлове
   npx dotenv-vault new
   npx dotenv-vault push  # криптира и качва
   npx dotenv-vault pull  # декриптира и сваля
   # Полезно ако имате множество среди и членове на екипа
   ```
   
   **Важно:** Никога не комитвайте .env файлове в Git! Проверете .gitignore:
   ```
   .env
   .env.local
   .env.production
   .env*.local
   ```

3. **Конфигуриране на vercel.json (ако е нужно)**
   ```json
   {
     "regions": ["fra1"],
     "headers": [
       {
         "source": "/(.*)",
         "headers": [
           { "key": "X-Frame-Options", "value": "DENY" },
           { "key": "X-Content-Type-Options", "value": "nosniff" }
         ]
       }
     ],
     "rewrites": [
       { "source": "/api/:path*", "destination": "/api/:path*" }
     ]
   }
   ```
   - `"regions": ["fra1"]` — Frankfurt регион, най-близо до България

#### Фаза 2: Деплой и тестване

4. **Първи деплой**
   ```bash
   # Локално (или чрез CI/CD от Git)
   vercel --prod
   
   # Vercel ще предостави URL: my-tonkin-xxxx.vercel.app
   ```

5. **Тестване на Vercel preview URL**
   - [ ] Всички страници зареждат ли се?
   - [ ] API routes отговарят ли правилно?
   - [ ] Автентикацията работи ли?
   - [ ] Интеграциите с външни услуги (payments, email и т.н.) функционират ли?
   - [ ] Производителност — Lighthouse тест
   - [ ] Мобилна версия

6. **Конфигуриране на custom domain**
   ```
   - Vercel Dashboard → Project → Settings → Domains
   - Добавяне на my.tonkin.bg
   - Vercel ще предостави CNAME запис за конфигуриране
   ```

#### Фаза 3: DNS промяна

7. **Намаляване на TTL** (7 дни предварително)

8. **DNS промяна**
   ```
   - CNAME запис: my.tonkin.bg → cname.vercel-dns.com
   - ИЛИ ако ползвате Cloudflare: A запис → Vercel IP (76.76.21.21)
   - Vercel автоматично издава SSL сертификат
   ```

9. **Деактивиране на стария Contabo VPS** (след 7 дни стабилна работа)

#### Бонус: Сигурност при миграцията на env файлове

| Практика | Описание |
|----------|----------|
| Ротация на API ключове | След миграцията, генерирайте нови API ключове за production |
| Audit log | Документирайте кой има достъп до env променливите |
| Vercel RBAC | Ограничете кой от екипа може да вижда/редактира env vars |
| Не логвайте secrets | Проверете кода за `console.log(process.env.*)` |
| Periodic rotation | Планирайте тримесечна ротация на ключовете |

## 5. Миграция на видео сървъра (100GB+ файлове)

### Предизвикателства

- **Обем:** 100GB+ видео файлове — трансферът отнема часове/дни
- **Активни cron задачи:** Автоматична обработка на записи от Zoom
- **Zoom webhook:** incoming.tonkin.bg трябва да приема POST заявки без прекъсване
- **HLS стрийминг:** Потребителите гледат видео в реално време — прекъсване е неприемливо
- **ffmpeg:** CPU-интензивна обработка, изисква правилна конфигурация

### Стъпка по стъпка

#### Фаза 1: Подготовка на новия сървър (3-5 дни)

1. **Провизиране на Hetzner Dedicated AX42**
   ```bash
   # След получаване на сървъра (обикновено 1-2 часа при Hetzner):
   
   # Инсталиране на OS
   # Ubuntu 22.04 LTS (чрез Hetzner Robot/installimage)
   
   # Основни пакети
   apt update && apt upgrade -y
   apt install -y nginx php8.2-fpm php8.2-cli php8.2-curl php8.2-mysql \
     ffmpeg rsync cron certbot python3-certbot-nginx htop iotop
   
   # Конфигуриране на firewall
   ufw allow 22/tcp    # SSH
   ufw allow 80/tcp    # HTTP
   ufw allow 443/tcp   # HTTPS
   ufw enable
   ```

2. **Конфигуриране на Nginx за HLS стрийминг**
   ```nginx
   server {
       listen 443 ssl http2;
       server_name incoming.tonkin.bg;
       
       # SSL сертификат (Let's Encrypt)
       ssl_certificate /etc/letsencrypt/live/incoming.tonkin.bg/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/incoming.tonkin.bg/privkey.pem;
       
       # HLS видео файлове
       location /videos/ {
           alias /var/www/videos/;
           types {
               application/vnd.apple.mpegurl m3u8;
               video/mp2t ts;
           }
           add_header Cache-Control "public, max-age=3600";
           add_header Access-Control-Allow-Origin "*";
       }
       
       # PHP скриптове (webhook, API)
       location ~ \.php$ {
           fastcgi_pass unix:/run/php/php8.2-fpm.sock;
           fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
           include fastcgi_params;
       }
       
       # Zoom webhook endpoint
       location /webhook/ {
           # ... PHP обработка
       }
   }
   ```

3. **Настройване на Hetzner Storage Box (бекъп)**
   ```bash
   # Монтиране на Storage Box чрез SFTP/SSHFS
   apt install sshfs
   mkdir /mnt/storage-box
   sshfs uXXXXXX@uXXXXXX.your-storagebox.de:/ /mnt/storage-box
   
   # Или за rsync бекъп:
   rsync -avz /var/www/videos/ uXXXXXX@uXXXXXX.your-storagebox.de:/videos-backup/
   ```

#### Фаза 2: Трансфер на видео файловете (5-7 дни)

4. **Начален rsync трансфер (най-голямата стъпка)**
   ```bash
   # От стария Contabo VPS към новия Hetzner Dedicated
   # Използваме rsync с --bwlimit за да не натоварим стария сървър
   
   # Стартиране в screen/tmux сесия (за да не прекъсне при загуба на SSH)
   tmux new -s migration
   
   rsync -avz --progress --partial --bwlimit=50000 \
     root@OLD_CONTABO_IP:/path/to/videos/ \
     /var/www/videos/
   
   # --partial: позволява продължаване на прекъснат трансфер
   # --bwlimit=50000: ограничение до ~50MB/s за да не натовари стария сървър
   # --progress: показва прогрес
   ```
   
   **Оценка на времето за трансфер:**
   - 100GB при 50MB/s ≈ ~35 минути (идеални условия)
   - Реално: 2-4 часа (с overhead, мрежови условия)
   - При по-бавна връзка (10MB/s): ~3 часа
   - **Планирайте трансферът да започне нощем** за минимално натоварване

5. **Миграция на PHP скриптове**
   ```bash
   rsync -avz --progress \
     root@OLD_CONTABO_IP:/path/to/php-scripts/ \
     /var/www/incoming.tonkin.bg/
   ```

6. **Миграция на cron задачите**
   ```bash
   # На стария сървър — експорт на crontab
   ssh root@OLD_CONTABO_IP "crontab -l" > old_crontab.txt
   
   # Преглед и адаптиране на пътищата
   # Примери:
   # Стар: */5 * * * * /usr/bin/php /var/www/html/process_zoom.php
   # Нов:  */5 * * * * /usr/bin/php /var/www/incoming.tonkin.bg/process_zoom.php
   
   # Инсталиране на новия crontab
   crontab new_crontab.txt
   ```

7. **Тестване на ffmpeg обработка**
   ```bash
   # Тестов файл
   ffmpeg -i test_input.mp4 \
     -codec:v libx264 -preset medium -crf 23 \
     -codec:a aac -b:a 128k \
     -hls_time 10 -hls_list_size 0 \
     -hls_segment_filename "test_%03d.ts" \
     test_output.m3u8
   
   # Проверка на производителността — колко FPS обработва
   ```

#### Фаза 3: Тестване без DNS промяна

8. **Тестване чрез hosts файл**
   ```
   NEW_HETZNER_IP    incoming.tonkin.bg
   ```
   
   Проверки:
   - [ ] HLS видеа се възпроизвеждат в браузър
   - [ ] PHP webhook endpoint отговаря правилно
   - [ ] ffmpeg обработва файлове коректно
   - [ ] Cron задачите се изпълняват по график
   - [ ] Nginx логове — няма 404/500 грешки

9. **Тестване на Zoom webhook**
   ```bash
   # Симулиране на Zoom webhook POST заявка
   curl -X POST https://incoming.tonkin.bg/webhook/zoom \
     -H "Content-Type: application/json" \
     -d '{"event": "recording.completed", "payload": {"test": true}}' \
     --resolve incoming.tonkin.bg:443:NEW_HETZNER_IP
   ```

#### Фаза 4: DNS промяна и финална синхронизация

10. **Инкрементален rsync** (непосредствено преди DNS промяна)
    ```bash
    # Този rsync ще прехвърли САМО новите/променените файлове от първоначалния трансфер
    # Ще бъде много по-бърз — минути вместо часове
    rsync -avz --progress --partial \
      root@OLD_CONTABO_IP:/path/to/videos/ \
      /var/www/videos/
    ```

11. **DNS промяна**
    ```
    A запис: incoming.tonkin.bg → NEW_HETZNER_IP
    ```

12. **Обновяване на Zoom webhook URL** (ако е необходимо)
    ```
    - Zoom Marketplace → App → Webhook настройки
    - Ако URL-то е incoming.tonkin.bg — не е нужна промяна (DNS ще сочи към новия IP)
    - Ако е с IP адрес — обновете с новия IP
    ```

13. **Мониторинг**
    ```bash
    # Следене на Nginx access/error логове
    tail -f /var/log/nginx/incoming.tonkin.bg-access.log
    tail -f /var/log/nginx/incoming.tonkin.bg-error.log
    
    # Проверка на cron изпълнения
    grep CRON /var/log/syslog
    
    # Мониторинг на дисково пространство
    df -h
    ```

### Стратегия за нулево прекъсване на стрийминга

```
Ден X-7:  Начален rsync трансфер (100GB+)
Ден X-3:  Втори rsync (само делта — нови файлове)
Ден X-1:  Финален rsync (минимална делта)
Ден X:    DNS промяна (5 мин TTL)
           → Потребители преминават плавно
           → Стар сървър все още работи за остатъчни DNS заявки
Ден X+3:  Последен rsync за файлове добавени в "прозореца"
Ден X+7:  Изключване на стария сървър
```

## 6. Трите най-големи риска и мерки за намаляване

### Риск 1: Загуба на данни при миграция на WordPress базата данни (15GB)

**Описание:** При 15GB MySQL база и активен сайт, между момента на експорт и импорт могат да се загубят данни — нови публикации, коментари, поръчки (ако има WooCommerce), потребителски регистрации.

**Вероятност:** Средна  
**Въздействие:** Високо — загубени данни може да са невъзстановими

**Мерки за намаляване:**

| # | Мярка | Описание |
|---|-------|----------|
| 1 | **Двуетапна синхронизация** | Първи експорт/импорт дни предварително. Финална синхронизация непосредствено преди DNS промяна (само делтата). |
| 2 | **Maintenance mode** | 30 мин преди финалния DNS switch — включване на maintenance mode на стария WordPress. Потребителите виждат "Сайтът се обновява", но не могат да пишат нови данни. |
| 3 | **Тройни бекъпи** | Бекъп на: (а) стария сървър, (б) Hetzner snapshot, (в) локално копие на SQL dump файла. |
| 4 | **Проверка на брояча на записи** | Преди и след миграцията: `SELECT COUNT(*) FROM wp_posts; SELECT COUNT(*) FROM wp_users; SELECT COUNT(*) FROM wp_options;` — числата трябва да съвпадат. |
| 5 | **Rollback план** | Ако нещо се обърка — DNS обратно към стария IP (5 мин TTL = бързо възстановяване). Старият сървър остава работещ минимум 7 дни след миграцията. |

### Риск 2: Прекъсване на Zoom webhook и видео обработка по време на уебинар

**Описание:** МАБИ провежда месечни уебинари. Ако миграцията на видео сървъра съвпадне с уебинар, Zoom webhook-ът може да не достави записа, или HLS стриймингът може да е недостъпен за участниците.

**Вероятност:** Висока (ако не се планира внимателно)  
**Въздействие:** Критично — пропуснат запис на уебинар не може да бъде възстановен

**Мерки за намаляване:**

| # | Мярка | Описание |
|---|-------|----------|
| 1 | **Забранен прозорец за миграция** | НИКОГА не правете DNS промяна в деня на уебинар и 24 часа преди/след него. Установете точните дати на уебинарите за юни и юли. |
| 2 | **Паралелен webhook** | Конфигуриране на Zoom webhook да изпраща и към стария, и към новия сървър (ако Zoom го поддържа). Алтернативно — middleware (напр. Cloudflare Worker), който препраща webhook-а и към двата сървъра. |
| 3 | **Zoom webhook retry** | Zoom автоматично повтаря неуспешни webhook доставки до 3 пъти в рамките на 30 мин. Ако DNS промяната е бърза (5 мин TTL), рискът е минимален. |
| 4 | **Бекъп план за записи** | Ръчно сваляне на записите от Zoom Cloud (запазват се 30 дни) като допълнителна мрежа за безопасност. |
| 5 | **Тестови webhook** | Преди реалната миграция — тест с Zoom test endpoint за потвърждение, че новият сървър приема webhook-ове коректно. |

### Риск 3: Изтичане на API ключове и секрети при миграцията

**Описание:** Преместването на env файлове с API ключове, database credentials, JWT секрети между сървъри създава прозорец за потенциално изтичане — особено ако ключовете се копират през несигурни канали (email, Slack, незащитен трансфер).

**Вероятност:** Средна  
**Въздействие:** Критично — компрометирани API ключове могат да доведат до финансови загуби, теч на данни на членовете

**Мерки за намаляване:**

| # | Мярка | Описание |
|---|-------|----------|
| 1 | **Сигурен трансфер** | САМО чрез SSH/SCP за копиране на env файлове. Никога по email, Slack, или незащитени канали. |
| 2 | **Ротация след миграция** | Веднага след успешна миграция — генериране на НОВИ API ключове за production. Невалидиране на старите. |
| 3 | **Vercel env vars** | За Next.js — ръчно въвеждане на стойностите в Vercel Dashboard (криптирано хранилище). Без копиране на .env файлове. |
| 4 | **Одит на достъпа** | Документиране кой има достъп до кои ключове. Премахване на достъпа на напускащия разработчик на 1 август. |
| 5 | **.gitignore проверка** | Проверка, че .env, .env.production, и подобни файлове са в .gitignore и НИКОГА не са били комитнати. Ако са — `git filter-branch` или `BFG Repo-Cleaner` за изчистване от историята. |
| 6 | **Инвентаризация на секретите** | Създаване на списък на всички API ключове, кой сервис ги ползва, и кога изтичат. Съхранение в password manager (1Password, Bitwarden). |

- [ ] Всички env променливи са мигрирани и ротирани
- [ ] Автоматичните бекъпи са конфигурирани и тествани
- [ ] Мониторингът е настроен (uptime + error alerts)
- [ ] Документацията е пълна и актуална
- [ ] Вътрешен човек е обучен и може да оперира самостоятелно
- [ ] Достъпът на външния разработчик е премахнат
- [ ] Старите сървъри са изключени
- [ ] DNS TTL е възстановен на нормални стойности
- [ ] Всички API ключове са ротирани след миграцията
